# Android 本周、阶段与列表改造

> 日期：2026-09-15  
> 数据库：v20 → v21  
> 主要平台：Android；Windows 同步数据结构与通用菜单规范

## 已完成内容

### 本周

- 每周固定以设备本地周一为起点，始终显示周一至周日七个标题，不再把空日期合并成“其余 N 天”。
- 空日期默认压缩为一行，可展开后直接添加到该日。
- 今天只显示未完成任务；过去日期和过去周同时显示原定当天的已完成与未完成任务。
- 同一天内在 Android 上长按任务排序；Windows 保留可见拖拽柄。
- 顶部“调整日期”进入跨日拖动状态，七个日期均可接收未完成任务。放下后只修改原任务的 `due_date` 和对应提醒日期，不复制任务、不修改阶段。
- 本周任务三点菜单为编辑、同步阶段、删除。“同步阶段”只修改 `task_mode`。
- 跨午夜时自动刷新“今天”判断；恢复本周页面时回到设备当前周。

### 阶段与详情

- Android 阶段任务改为长按整行进行组内排序。
- 跨阶段仍通过三点菜单；菜单保留编辑、移到其他阶段、移回列表和删除，并增加“同步今日”。
- “同步今日”只把 `due_date` 更新为设备本地今天并重排提醒，保留原阶段。
- 点击任务继续进入以子任务为主的详情页；详情页右上角增加“编辑”，复用完整编辑表单。

### 列表与最近删除

- “筛选与统计”的智能视图按收件箱、已完成、最近删除、精灵窝排列。
- 收件箱只显示未完成且未安排的任务；已完成、最近删除和精灵窝为独立视图。
- Todo 列表取消滑动完成，只保留向左滑出的操作入口，降低误触概率。
- 最近删除改为显示实际删除日期，移除没有自动清理支撑的“剩余 15 天”文案。
- 永久删除增加明确确认；任务不再因完成 7 天或删除 15 天而自动永久清理。

### 页面记忆与菜单

- Android 在 `settings` 表保存上次根页面（备忘录/Todo）、Todo 一级页面（列表/安排）及智能视图或阶段/本周。
- 不恢复任务详情、搜索词、临时筛选和本周偏移，避免重开后进入过时上下文。
- 应用内三点图标统一为 `more_vert`、22dp 图标和至少 48dp 触控区；操作按编辑、移动/同步、分隔线、删除排列。
- Android 原生桌面小部件同步了操作顺序和本周排序读取；小部件仍使用系统原生菜单。

## 当前架构

- `Task.taskMode` 决定阶段，`Task.dueDate` 决定本周日期，两处始终引用同一条任务记录。
- `sort_order` 服务于列表与阶段，v21 新增 `week_sort_order` 服务于同一天的本周排序，避免一个视图的拖动扰乱另一个视图。
- `TaskArrangementView` 负责固定七天、历史完成可见性、长按排序、跨日拖动和阶段/本周菜单。
- `TodoScreen` 负责数据加载、提醒取消与重排、智能视图、页面状态持久化及服务调用。
- `TaskRepository` 以事务更新同日排序；跨日移动把任务追加到目标日期末尾并递增同步修订号。
- SQLite outbox 和 Supabase `app_records.payload` 会携带 `week_sort_order`；旧云端/旧 JSON 没有该字段时回退本地值或 `sort_order`。
- Android `WidgetTaskStore` 在 v21 使用 `week_sort_order`，检测到旧库字段不存在时回退 `sort_order`。

## 数据迁移与维护

- `DatabaseProvider` 当前版本为 21。首次打开现有 v20 文件库前，在同目录创建 `todo_list.db.pre-v21`；若 WAL/SHM 存在则一并复制。
- v21 迁移添加 `week_sort_order INTEGER NOT NULL DEFAULT 0`，并用现有 `sort_order` 初始化，保证旧任务初始顺序稳定。
- JSON 导入和同步合并都必须保留旧数据回退；以后新增任务排序字段时，要同步检查模型、建表、迁移、导入、云 payload 和 Kotlin 小部件六处。
- 页面记忆属于设备偏好，只写 `settings`，不进入 Supabase 同步。
- 本周日期以设备本地时区为准；业务层比较前统一截断到年月日。

## 验证结果

- `flutter test --no-pub --concurrency=1`：55/55 通过。
- 覆盖固定七天、今天隐藏完成、过去日期保留完成、本周独立排序、跨日只改日期、v20→v21 备份与迁移、列表仅单方向滑动等回归。
- `test/goldens/stage_mobile.png` 与 `test/goldens/week_mobile.png` 已按 390×844 更新并人工检查，无溢出、遮挡和触控入口拥挤。
- `dart analyze lib test`：无新增错误；仍有 `supabase_sync_gateway.dart` 两条既有 `unawaited_return_in_try_block` warning 和若干既有 info。
- Windows Release 构建成功：`build/windows/x64/runner/Release/todo_list.exe`。
- Codex 子进程内 Android Release 构建曾因 JBR NIO/AF_UNIX 报 `Unable to establish loopback connection`；小花先生随后在普通终端运行同一命令成功。新 APK 已通过 ZIP 结构和 v2 签名校验，仍未进行真机截图与拖动手感验收。详见 `docs/2026-09-15-Gradle回环连接诊断.md`。

## 潜在问题

- 跨日拖动依赖长列表边缘自动滚动，组件测试覆盖业务结果，仍需真机确认不同屏幕密度下的拖动手感。
- 页面恢复仅在 Android 启用；进程被系统强杀时 SQLite 写入通常可靠，但仍需装机覆盖备忘录、列表、已完成、阶段、本周五类退出场景。
- 列表加载仍逐条读取子任务进度，并在刷新时重复处理提醒；大量任务时可能产生可感知延迟。
- 当前无 Android 设备或 AVD，小部件、系统返回手势、原生菜单和提醒日期联动仍属于装机验收项。

## 下一步优化建议

1. 优先增加“逾期未完成集中处理”，统一查看旧周遗留任务，并提供批量改到今天。
2. 评估常用任务模板，减少重复录入日常任务。
3. 批量查询子任务进度，并只在任务日期或提醒属性变化时更新系统提醒。
4. 侧装当前 Android Release，集中验收固定七天、跨日拖动、阶段同步今日、页面恢复、最近删除确认和两个桌面小部件。

## 可复用经验

- 同一实体出现在多个视图时，业务属性和视图排序必须分开建模；阶段、日期和各自排序不能复用一个字段。
- 历史回看规则要从数据源开始设计。若上层只传未完成任务，界面无法补出过去完成记录。
- “看起来有倒计时”的文案必须有真实清理任务支撑；没有清理机制时应显示事实日期。
- 组件基准图只能证明布局稳定，不能替代 APK 构建、安装和真机手势验收。
