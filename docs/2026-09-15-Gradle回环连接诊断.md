# Gradle 回环连接诊断

> 日期：2026-09-15  
> 结论：Codex Windows 子进程环境中的 JBR NIO/AF_UNIX 通信异常，不是项目代码、Gradle 依赖下载或系统 TCP 回环故障

## 现象

- Codex 内执行 Android Release 构建时，Gradle 报 `java.io.IOException: Unable to establish loopback connection`。
- 小花先生随后在普通终端执行同一构建命令成功，生成了 2026-09-15 12:41 的新 APK。

## 日志证据

失败日志位于 `C:\Users\yjhdetianxuan\.gradle\daemon\9.1.0\daemon-28420.out.log`。完整异常链为：

```text
WEPollSelectorImpl.openSelector
PipeImpl$Initializer.run
UnixDomainSockets.connect0
java.net.SocketException: Invalid argument: connect
```

表层文字虽然写着 loopback，但实际失败点是 JBR 21 在 Windows 上为 NIO Selector 建立内部唤醒管道时使用的 AF_UNIX 本地套接字，不是应用访问远端 Maven，也不是普通 TCP 端口连接。

成功日志位于 `daemon-34220.out.log`，使用相同的 JBR 21.0.10、Gradle 9.1.0 和项目目录，并返回 `Success`。这排除了项目配置、JDK 版本和依赖文件本身的持续性故障。

## 本机检测

- PowerShell 创建 IPv4 `127.0.0.1` 和 IPv6 `::1` 监听与客户端连接均成功。
- 动态 TCP 端口范围正常：49152 起，共 16384 个。
- `hosts` 没有重写 localhost；其中对其他站点的屏蔽条目与本次 JBR AF_UNIX 异常无关。
- JBR 路径存在，版本为 `21.0.10`。
- Codex 进程内 Gradle 使用隔离的 `C:\Users\CodexSandboxOffline\.gradle`；普通终端构建使用真实用户目录。执行上下文是成功与失败之间的关键变量。

## 处理原则

- 不修改应用代码、Gradle 配置、防火墙、hosts 或 Winsock。
- Codex 中若再次出现同一异常，直接把它归类为工具执行环境阻断，不反复下载依赖或清缓存。
- Android 正式构建改由普通 PowerShell 或 Android Studio 执行；Codex 继续负责代码测试、静态检查和产物校验。
- 若普通终端也连续出现同一底层堆栈，再单独检查 JBR、TEMP 路径和安全软件；本次没有该证据。
