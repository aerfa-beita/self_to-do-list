# 2026-09-16 Android 应用内更新与正式签名

## 已完成内容

- Android 冷启动每 24 小时检查一次 GitHub Releases；“更多”菜单支持手动检查。
- 更新弹窗显示目标版本、安装包大小、更新内容、下载进度、取消、重试和安装入口。
- 下载只接受 GitHub 的 HTTPS 地址及受信任的 Release 资源跳转。
- 安装前依次核对文件大小、SHA-256、包名、`versionCode`、`versionName` 和当前应用签名证书。
- 校验失败或取消下载时删除临时 APK；APK 只能从应用缓存的 `updates` 目录交给系统安装器。
- Android 8+ 未授权“安装未知应用”时打开当前应用的系统授权页；最终安装仍由 Android 系统确认，应用不做静默安装。
- 版本升级到 `1.3.0+6`，Release 构建改用正式签名；缺少本地签名配置时直接拒绝构建，不再回退到调试证书。
- 增加 `scripts/publish_android_release.ps1`：构建正式 APK、计算 SHA-256、创建草稿 Release、上传 APK、最后上传版本清单并发布。

## 当前架构

```text
App 冷启动 / 更多 > 检查更新
  → AppUpdateService 读取 update-manifest.json
  → 比较 versionCode
  → 下载到 cache/updates/app-update.apk
  → 大小 + SHA-256 校验
  → MainActivity 校验包名 + 版本 + 签名证书
  → FileProvider 只读 URI
  → Android 系统安装确认
```

GitHub Release 固定包含：

- `xiaohua-todo-<versionName>.apk`
- `update-manifest.json`

版本清单字段固定为 `versionName`、`versionCode`、`minSupportedVersionCode`、`apkUrl`、`sha256`、`sizeBytes`、`changelog`、`publishedAt`。

## 正式签名与首次迁移

- 正式密钥：`android/app/todo-release.jks`，本地配置：`android/key.properties`；两者均被 Git 忽略。
- 已在 `.local-backups/android-signing-20260916/` 建立本机恢复副本。该副本与主密钥仍在同一台电脑，不能替代异地加密备份。
- 手机现有版本使用调试签名，无法直接覆盖安装正式签名版。首次迁移必须：
  1. 在旧版中导出 JSON 备份并核对文件可读。
  2. 卸载旧调试签名版。
  3. 安装首个正式签名 APK。
  4. 合并导入 JSON，并检查任务、备忘录、阶段、本周和提醒。
- 完成首次迁移后，只要一直保留同一正式密钥，后续版本即可通过应用内下载并覆盖安装。

## 发布维护方式

1. 更新 `pubspec.yaml`，保证 `versionCode` 严格递增。
2. 确认 `android/key.properties` 和正式密钥可用，并完成测试与 Android Release 构建。
3. 在本地终端临时设置 `GITHUB_TOKEN`；Token 只需要当前公开仓库的 Release 写入权限，不写入文件和 Git。
4. 执行：

```powershell
.\scripts\publish_android_release.ps1 `
  -VersionName 1.3.0 `
  -VersionCode 6 `
  -MinSupportedVersionCode 5 `
  -Changelog "本周历史任务修复；安排页改版；加入应用内更新"
```

脚本先创建草稿 Release 并上传 APK，确认资源成功后才上传 `update-manifest.json`，最后公开 Release。发布中断会留下草稿，不会让客户端读取到半成品更新。

## 潜在问题与下一步

- 需在普通 PowerShell 或 Android Studio 执行 `flutter build apk --release`，核对 APK 版本、包名、签名和生成时间。
- 正式发布前必须把签名密钥与密码做一份离线或加密异地备份；密钥丢失后无法覆盖升级现有正式安装。
- 首个正式签名版需按“导出—卸载—安装—导入”完成一次真机数据迁移。
- 使用第二个更高 `versionCode` 的测试 Release，逐项验收检查、下载、取消、断网、摘要不匹配、未知来源授权、系统安装确认和覆盖升级。
- GitHub Release 尚未发布；发布属于外部可见操作，需在 APK 和真机链路通过后再执行。

## 可复用取舍

- 客户端只信任固定发布域名、清单摘要和当前签名证书，版本清单本身不能绕过 APK 身份检查。
- 上传顺序采用“APK 在前、清单在后”，降低客户端看到不可下载版本的窗口。
- 最低支持版本只加强提示，不锁死“稍后”，避免网络或发布事故让用户无法进入本地数据。
- Release 构建缺密钥时失败，比静默回退到调试签名更容易维护长期升级链。
