# Android 自动更新检查反馈修复

## 已完成内容

- Android 启动后自动检查更新；只有检查成功后才记录时间，24 小时内不重复自动请求。
- 自动检查失败时保持静默，避免每次启动打扰；发现新版时显示更新弹窗。
- 手动点击“检查更新”立即显示“正在检查更新”，并最终明确反馈最新版、网络失败、超时、证书错误、HTTP 状态或缺少发布清单。
- 手动检查与启动自动检查重叠时，不再吞掉点击；当前请求会接管手动反馈。
- 更新清单请求增加 15 秒总超时，覆盖连接、响应和正文读取。
- 更新始终为非强制：即使当前版本低于清单的最低兼容版本，也保留“稍后”和返回关闭能力。

## 当前架构

1. `main.dart` 负责 24 小时间隔、自动/手动检查协调和界面反馈。
2. `AppUpdateService` 负责可信 GitHub 地址、网络请求、总超时、清单解析和错误归类。
3. `AppUpdateDialog` 负责版本说明、稍后、下载、校验和系统安装。
4. `scripts/publish_android_release.ps1` 负责发布 APK 与 `update-manifest.json`；客户端没有有效清单时不能判断新版本。

## 验收结果

- 更新服务与弹窗专项测试通过。
- 完整 Flutter 测试 82/82 通过。
- `flutter analyze --no-pub` 保持 17 条既有提示，本次未新增静态问题。
- Windows Release 构建成功：`build/windows/x64/runner/Release/todo_list.exe`。
- Android Release 在 Codex/JBR 环境启动 Gradle 时仍报既有 `Unable to establish loopback connection`；错误发生在 Dart/Kotlin 编译前，本批没有宣称 APK 构建通过。

## 维护方式

- 修改检查时限时调整 `AppUpdateService.checkTimeout`，测试可注入清单和已安装版本，不发真实网络请求。
- 发布新版本时必须先上传 APK，再上传清单；清单中的版本、大小、SHA-256 和下载地址必须与 APK 一致。
- `android_last_update_check` 只表示最近一次成功检查，不能在请求前写入。

## 潜在问题与下一步

- 首个可用更新仍依赖 GitHub Release 中真实存在的 `update-manifest.json`。
- 正式签名 APK 的覆盖升级、断网、代理网络、摘要不匹配和未知来源授权仍需真机验收。
- GitHub 在部分网络环境下不可达时，应用会在 15 秒内结束检查并提示检查网络或代理；后续可增加国内只读镜像，但不能降低签名和摘要校验。

## 可复用经验

- 自动检查和手动检查共享同一请求时，必须保留手动反馈意图，不能用“正在请求”状态直接丢弃点击。
- 节流时间应在成功后记录；失败也记录会让临时网络故障变成 24 小时不再检查。
- 连接超时不等于完整请求超时，响应正文读取也必须被总时限覆盖。
